# Project lifecycle and recovery

## Review boundaries

The project lifecycle extraction is in `app/renderer/src/project/{snapshots,document,safety,lifecycle}.js` and its adapters in `boot.js`. The recovery feature is in `{recovery,recovery-ui}.js`, the main-process recovery store and IPC registrar, native close routing, and recovery markup/translations. These are separate review surfaces; no unrelated working-tree changes need to be included when reviewing this work.

Modules are classic scripts registered under `window.SoapyPanels.project`; all controllers except the DOM recovery chooser also have CommonJS exports. Factories receive explicit adapters for state, media encoding, restoration, dialogs, clocks, and I/O. `boot.js` retains rendering, media hydration/disposal, and undo-stack internals. It exposes thin Save/Save As/Open/New wrappers and awaits restoration completion before lifecycle replacement.

## Behavior

Recovery is enabled in both Electron editions. It never overwrites a `.soapy` file or changes that file's schema. Captures include bubbles, backgrounds, PNG/JPEG/etc. images, GIF source bytes, masks, effects, and saved styles. MP4 layers and undo history are excluded. The chooser discloses the excluded video count.

After a document edit, capture is scheduled for five seconds of inactivity, no later than thirty seconds into continued editing. Active gestures and restoration defer capture until they finish. History commit/scheduling/restore adapters signal edits; a one-second comparison catches changes outside history. Selection, viewport, and UI preferences are excluded. Draft changes in dialogs are recoverable after they are applied to the document.

A capture detaches document values and retains immutable Blob references before asynchronous media conversion. All recovery media is embedded as data URLs; source encodings are reused until their source changes. Only one recovery conversion/write is active. New/Open/Save/Close fence pending work with generations and epochs. Errors leave the last durable snapshot intact and report a nonmodal status. Transient I/O failures retry after thirty seconds. Size, storage, and session quota failures pause automatic captures until the user explicitly selects Retry (or successfully saves/replaces the project).

There are two independent saved-state baselines. Export preserves its previous behavior of acknowledging the unsaved warning. Only an editable project save acknowledges the file baseline or clears recovery. A save acknowledges precisely its captured revision, so edits made during saving remain unsaved and recoverable. Undoing back to the file baseline removes obsolete recovery.

New/Open clear the outgoing recovery only after the transition succeeds. Canceling leaves it intact. Native close, application close, and quit all use an asynchronous confirmation/cleanup handshake; an approved orderly close removes current recovery, including after export. A process/renderer crash retains it. Recovery guarantees the last completed snapshot, not the last keystroke.

Startup waits for language selection, then discovers interrupted sessions before trying to allocate a new session. Discovery still works when storage or session capacity is exhausted. Users can leave the chooser without deleting copies and keep editing or saving. File → Manage recovery copies reopens it; listings are paginated in groups of 32, with damaged snapshots offered for explicit discard only. Recover restores an unsaved document without its original file handle and starts a fresh undo history. The claimed backup is retained until a replacement snapshot is durable or the document is saved/discarded. Recovering one of several sessions leaves other copies available on a later launch.

## Storage and trust boundary

Storage lives at `<Electron userData>/project-recovery/<opaque session UUID>/`. The main process chooses all paths. Renderer APIs do not accept filesystem paths. Every recovery handler uses the existing trusted-main-frame IPC registrar; ownership additionally binds session IDs to the requesting WebContents.

Snapshot envelope version 1 contains `version`, `timestamp` (main-generated ISO date), `name`, `generation`, `revision`, `excludedVideoCount`, and `project` (ordinary project data). Only these seven envelope fields are serialized. Version and timestamp are generated by the main process. The existing resource validator and 256 MiB UTF-8 project payload limit apply, along with a 256 MiB + 4 KiB limit on the entire serialized snapshot. Reads use the same ceiling, check file size before opening, and bound reads if files grow. Legacy unknown envelope fields are ignored after a bounded read; oversized/corrupt newest snapshots fall back to earlier valid copies. Temporary media references are rejected.

Writes use a private temporary file, file sync, atomic rename, and directory sync where supported. Two valid completed snapshots are retained; reading falls back from a corrupt latest snapshot. Saved revisions have a durable floor preventing old queued writes from recreating cleared content. Discard fences queued writes before deleting the session.

The profile has a 2 GiB logical-file-byte budget, 32 session directories, and at most two owned sessions per renderer (current work plus a claimed backup). Two completed snapshots are retained. Admission includes the full new temporary snapshot before pruning either previous copy. There is no eviction to make room. Repeated start calls return the renderer's current session; oversized legacy profiles remain discoverable, readable, claimable, and explicitly discardable, but cannot admit new sessions or snapshots until capacity is available.

Three MiB of the budget is reserved for control metadata: 64 KiB per session plus 1 MiB for coordination and sidecars. Individual control records are capped at 4 KiB; new sessions use compact ownership/floor/release records. Excess legacy metadata is charged as data until safe compaction succeeds. Quotas measure logical file lengths, not filesystem blocks, total process memory, SQLite caches, or project files outside recovery storage. Test-only factory options can reduce limits but cannot raise them; production IPC exposes no limit configuration.

`recovery-coordinator.js` uses bundled `node:sqlite` with `BEGIN IMMEDIATE` in `project-recovery/.control/quota.sqlite`. The lock spans filesystem accounting, admission, temporary writes, publication, and cleanup. SQLite releases coordination after process death; no timeout-based filesystem lease takeover is used. The filesystem remains the byte-count authority. Snapshot submissions fail busy before payload serialization when another operation is pending; control operations have bounded lock retries. Each renderer has one pending operation plus one draining lifecycle cleanup, preventing unbounded payload queues. Unsupported or unavailable coordination fails closed for recovery while the editor remains usable.

Ownership is checked under this profile-wide lock. Claims compact legacy ownership chains into the current record, preserving snapshots. Live or ambiguous process owners are protected; renderer termination/navigation writes an explicit release marker. Close **all older app versions** before upgrading: older versions do not participate in SQLite coordination. Automatic cleanup removes only recognized abandoned temporary files and empty inactive session directories; it never follows links or discards recoverable snapshots merely to regain capacity. Explicit discard can remove an inactive copy without first allocating an ownership slot. Single-session release preserves a failed restoration's copy. Disposal stops admission and drains operations through the existing five-second quit coordinator; interrupted work remains available at the next startup.

### Preload additions

| Method | Meaning |
| --- | --- |
| `recoveryStart()` | Allocate a main-owned session and return its UUID. |
| `recoveryList({cursor})` | Return `{sessions, nextCursor, usage}` with at most 32 inactive entries, including damaged copies. |
| `recoveryClaim(id)` | Exclusively claim an interrupted session for this renderer. |
| `recoveryRead(id)` | Read the newest valid owned snapshot, falling back when needed. |
| `recoveryWrite(id, envelope)` | Validate and durably write a newer revision (or retry an identical revision); return whether accepted. |
| `recoveryClear(id, {generation, revision})` | Clear only snapshots through the saved revision and fence stale writes. |
| `recoveryDiscard(id)` | Fence and delete an owned or verified inactive session. |
| `recoveryRelease(id)` | Relinquish one owned session without deleting its backup. |
| `onProjectCloseRequested(callback)` | Receive native close/quit requests, including requests queued during renderer loading. |
| `projectCloseResult(approved)` | Complete the native close handshake. |

Recovery IPC wraps results internally as `{ok,value}` or `{ok:false,error:{code,message}}`; preload unwraps successes and reconstructs failures. Renderer quota handling supports the stable error-code prefix when Electron strips custom error properties. Trusted sender validation still precedes dispatch.

## Validation

Focused unit tests cover document commands, dirty baselines, detached snapshots, safety dialogs, scheduling, retry, stale writes, corruption, disk failures, and competing claims. Integration coverage verifies trusted IPC rejection and preload/shared channel parity. Electron tests use isolated temporary profiles and forced process termination to cover recovery with images/GIFs, save versus export cleanup, native close cancellation/quit, deliberate discard, and MP4 disclosure.

Run `node --test test/unit/project-*.test.js test/integration/project-recovery-ipc.test.js` and `node --test --test-concurrency=1 test/e2e/project-recovery.test.js`. The usual repository test runners also discover these files.
